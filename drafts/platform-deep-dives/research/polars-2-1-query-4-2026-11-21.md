# Polars 2.1 on TPC-DS: one query behind the result (2026-11-21)

Companion to `outlines/polars-2-version-matrix.md`. Earlier notes left "why
does 2.1.0 need more memory than 2.0.0 on TPC-DS" open. This note answers it
as far as our data and the Polars repository allow.

- Query 4 by run, default engine: 2.0.0 4.37, 4.67, 5.28; 2.1.0 10.22,
  10.28, 10.95. It is 2.2 times slower on 2.1.0 in all six runs.
- Summed per-query medians differ by +3.58 s between the releases on the
  default engine; query 4 alone is +5.61 s. No other query moves by more than
  0.7 s.
- The other 102 queries take 7.8% less time on 2.1.0 on the default engine
  and 10.1% less on streaming.
- Query 11 has the same shape with two channels instead of three and takes
  1.89 s on 2.0.0 and 1.90 s on 2.1.0.

## Query 4 in BenchBox

`_year_growth_expression` in
`benchbox/core/tpcds/dataframe_queries/queries.py`: `year_total` is a
`concat` of three per-channel group-by results (store, catalog and web sales
by customer and year). The query then filters `year_total` six times, once
per channel and year, and joins the six results on customer.

So it has a union of group-by results and one result read by six consumers.

## Query 4 on its own (R28)

One run per case, `--queries 4`, default engine, with
`POLARS_OOC_LOG_METRICS=1`. The machine was busy: other sessions held swap at
about 9 of 10 GB, and admission to the heavy-work lock took over 30 minutes.

| Case | Outcome |
|---|---|
| 2.0.0, default settings | Finished. 7.25 s warm-up, 7.15 s measured. No context wrote to disk. |
| 2.1.0, `POLARS_OOC_MEMORY_BUDGET_MB=4000` | Stopped during the warm-up pass by the heavy-work watchdog at critical memory pressure. The Python process had a footprint of 7.60 GiB. The `in-memory-sink` context had looked for data to write to disk 1,414 times and found none. |
| 2.1.0, default settings | Not run; the stop above ended the job. |

Limits of this test: one run each; a busy machine; the 2.0.0 footprint was
not captured (the sampler in `q4.py` could not read child memory and
recorded zero); the group-by contexts had not printed their statistics when
the 2.1.0 run was stopped, so the log does not show which operator held the
memory.

An earlier full TPC-DS run on 2.1.0 the same morning was stopped by the same
watchdog at a tree footprint of 9.16 GiB, 18 seconds in.

## What the post may say

- One query explains the 2.1 TPC-DS result, with the table above.
- The query's shape, and that it finished alone on 2.0 without writing to
  disk while on 2.1 it reached 7.6 GiB under a 4 GB Polars budget before a
  guard stopped it.
- 2.1 rewrote the streaming group-by (R29); two open upstream reports
  describe higher memory on 2.1 for unions and for results read by several
  consumers (R30); both match the query's shape.
- Not established: which of these is the cause. We did not trace the query
  inside Polars. Say that in one clause and do not pose it as a question.
- More group-by memory work has merged and is unreleased (R31). Do not say it
  fixes this query.

This supersedes two rules in earlier notes: the post may give 2.1.0's TPC-DS
time (34.1 s median of three runs), with the disk and swap figures beside it.
