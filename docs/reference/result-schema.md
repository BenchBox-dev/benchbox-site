# Result Bundle Schema (2.4)

A BenchBox result bundle is the JSON file that `benchbox run` writes for one run. This page is the reference for the current bundle version, **2.4**, and for the machine-readable JSON Schema that validates it. For a tour of the fields with examples, see [Result Formats](result-formats.md). The older v1.1 shape is described on the [legacy schema page](result-schema-v1.md).

## The schema file

The JSON Schema (draft 2020-12) is generated by BenchBox from the same definitions its own validator uses, so it cannot drift from what BenchBox accepts. It is published at a stable URL:

```text
https://benchbox.dev/schemas/result-bundle-2.schema.json
```

The `2` in the file name is the bundle's major version, which is the compatibility unit (see [Compatibility within major version 2](#compatibility-within-major-version-2)). The schema document carries the current result schema version in its top-level `result_schema_version` key (`"2.4"`), and its `$id` is the URL above. One schema validates every bundle that BenchBox 2.x accepts: the `result_schema_version` property lists the accepted versions `2.0` to `2.4`, and version-gated rules apply only to the versions that introduced them.

## Validate a bundle

Download the schema once, then validate a bundle. With `ajv-cli`:

```bash
curl -fsSLO https://benchbox.dev/schemas/result-bundle-2.schema.json
npx ajv-cli@5 validate --spec=draft2020 --strict=false -s result-bundle-2.schema.json -d my-run.json
```

`--strict=false` is needed because the schema carries a top-level `result_schema_version` marker that strict mode does not know. With Python:

```bash
python -m pip install jsonschema
python -c "import json, jsonschema; jsonschema.validate(json.load(open('my-run.json')), json.load(open('result-bundle-2.schema.json')))"
```

A valid bundle prints `my-run.json valid` (ajv) or nothing (jsonschema). An invalid one exits non-zero and names the path and rule, for example `must have required property 'id'` at `/run`.

> [!NOTE]
> The schema checks structure: required keys, types, version gating and the closed top-level key set. The BenchBox validator (`benchbox results validate`) enforces more than JSON Schema can express, for example that `row_count_validation.actual` equals the query's `rows`, that `result_schema_version` and `version` agree when both are present, and that `run.net_estimate_status` of `eligible` needs a networked endpoint. The `description` field of the schema lists these omissions. A bundle that passes the schema can still fail `benchbox results validate`.

## Top-level blocks

The top level is closed: a key that is not listed here fails validation.

| Key | Required | Contents |
| --- | --- | --- |
| `result_schema_version` | one of this or `version` | Bundle version string, `"2.4"` for current bundles. |
| `version` | one of this or `result_schema_version` | Legacy spelling of the version. Current bundles write both, and they must match. |
| `run` | yes | One run: identifier, timestamp, durations, iteration and stream counts, timing method. |
| `benchmark` | yes | Benchmark identity and scale factor. |
| `platform` | yes | The platform under test: name, version, deployment, compute, configuration. |
| `summary` | yes | Aggregate query counts and timing statistics. |
| `queries` | yes | One entry per query execution, including warm-up. |
| `environment` | no | The client host, link and host-load samples. |
| `config` | no | Run configuration: phases, query subset, platform options. |
| `phases` | no | Duration and status of data generation, loading, power and throughput phases. |
| `tables` | no | Table statistics. |
| `execution` | no | Driver, translation and tuning-mode metadata. From 2.6, `execution.timeout` records the run time limit (`timeout_seconds`, `phase`, optional `query_id`) of a run that stopped at its limit; such a run has `summary.validation` set to `timed_out`. |
| `tuning` | no | Tuning configuration applied to the run. |
| `cost` | no | Cost information. |
| `normalized_cost` | no | Cost normalized to a common model. |
| `provenance` | no | Provenance of the run. |
| `export` | no | Exporter tool, BenchBox version and timestamp. |
| `errors` | no | Errors recorded during the run. |
| `comparisons` | no | Comparison records. |
| `tpc_compliant` | no | Whether the run followed a TPC specification. |

## Required keys inside blocks

| Block | Required keys |
| --- | --- |
| `run` | `id`, `timestamp`, `total_duration_ms`, `query_time_ms` |
| `benchmark` | `id`, `name`, `scale_factor` |
| `platform` | `name` |
| `summary` | `queries`, `timing` |

Keys inside these blocks beyond the required ones are optional, and most blocks accept keys the schema does not name. The closed objects are the top level, the `environment.host_load` samples, the `platform_timing` objects and the `row_count_validation` object.

## Queries

`queries` is an array. Each entry describes one execution of one query. Keys BenchBox writes include:

| Key | Meaning |
| --- | --- |
| `id` | Query identifier. |
| `ms` | Execution time in milliseconds. |
| `rows` | Rows returned. |
| `iter`, `stream`, `run_type` | Iteration number, stream number and `warmup` or `measurement`. |
| `status` | `SUCCESS`, `SKIPPED` or a failure status. |
| `row_count_validation` | Optional, from 2.2. Expected and actual row counts and a status. |
| `request_count`, `result_bytes` | Optional, from 2.4. Non-negative integers. |
| `platform_timing` | Optional, from 2.4. Platform-reported timing with a `status` of `valid`, `suspect` or `unavailable`. |

## Host load

From 2.4 bundles can carry `environment.host_load`, which records the state of the machine that ran the benchmark at the start and at the end of the run. It exists so that a reader can tell whether a slow run happened on a busy or throttled host. The samples are taken outside the measured intervals.

```json
"environment": {
  "host_load": {
    "start": {
      "load_average": [0.42, 0.51, 0.48],
      "cpu_frequency_mhz": 3200.0,
      "memory_available_mb": 11264.0,
      "swap_used_mb": 0.0,
      "swap_percent": 0.0,
      "sampled_at": "2026-11-12T16:00:00.120000"
    },
    "end": {
      "load_average": [1.9, 0.9, 0.6],
      "cpu_frequency_mhz": 3100.0,
      "memory_available_mb": 11010.0,
      "swap_used_mb": 0.0,
      "swap_percent": 0.0,
      "sampled_at": "2026-11-12T16:00:14.920000"
    }
  }
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `load_average` | array of numbers, or `null` | The 1, 5 and 15 minute load averages. |
| `cpu_frequency_mhz` | number or `null` | Current CPU frequency. |
| `memory_available_mb` | number or `null` | Memory available on the host. |
| `swap_used_mb` | number or `null` | Swap in use. |
| `swap_percent` | number or `null` | Swap in use as a percentage. |
| `sampled_at` | string or `null` | Timestamp of the sample. |

When `host_load` is present, `start` and `end` are both required and each carries all six fields. A value the platform cannot report is an explicit `null`, never a missing key. Bundles written before the field existed carry no `host_load`, and the schema does not require it.

## Version history

| Version | Change |
| --- | --- |
| 2.6 | Optional `execution.timeout` (`timeout_seconds`, `phase`, `query_id`) for a run that stopped at its run time limit. |
| 2.4 | Optional per-query `request_count`, `result_bytes` and `platform_timing`; run-level `timing_method`, `platform_timing` and `net_estimate_status`; `environment.client_link`; `environment.host_load`. |
| 2.3 | Optional execution-engine receipts, compute size, deployment, gateway and variant identity. |
| 2.2 | Per-query `row_count_validation`; the version key is `result_schema_version`, with `version` as the legacy spelling. |
| 2.1 | Typed result and companion metadata. |
| 2.0 | First v2 bundle contract. |

The schema rejects a field in a bundle whose version predates it, for example `row_count_validation` in a 2.1 bundle.

## Compatibility within major version 2

The URL names the major version, so a pipeline that validates against `result-bundle-2.schema.json` keeps working while major version 2 lives.

**Compatible changes** keep every bundle that was valid under an earlier 2.x version valid. They raise the minor version (2.4 to 2.5) and are published at the same URL:

- adding optional keys or optional blocks,
- adding values to enums that the schema marks as open,
- raising the minor version.

**Breaking changes** need major version 3, published at a new URL with a `3` in its name. The version 2 URL keeps serving the version 2 schema. Breaking changes are:

- removing or renaming a required key,
- changing the type of an existing key,
- narrowing the set of accepted values,
- changing what an existing key means.

What this means for consumers:

- **Ignore keys you do not recognize** inside blocks, and do not rely on key order. A later 2.x bundle can carry keys that 2.5 does not know.
- **The schema's top level is closed.** The published schema is the newest 2.x, and it sets `additionalProperties: false` for the top level, as BenchBox's validator rejects unknown top-level keys. A bundle from a newer BenchBox that adds a top-level block validates against the schema published with that release. Fetch the schema again when you upgrade BenchBox, or pin the schema file you validated against.
- **Older BenchBox releases reject newer minors.** The runtime accepts only the versions it knows (currently 2.0 to 2.6) and fails closed on others, so a 2.7 bundle needs a BenchBox release that knows 2.7 to be read. Only the public submission check accepts any numeric 2.x version.

## Legacy

Bundles written before 2.0 use the v1.1 shape, described on the [legacy schema page](result-schema-v1.md). BenchBox reads them only through a best-effort normalizer. The JSON Schema on this page does not cover them.
